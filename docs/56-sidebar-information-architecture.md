# docs/56：侧边栏的信息架构 —— 按任务流排，不按使用频率排

用户第 323 轮原话（逐字）：

> 侧边栏几个页面重新排序一下，现在这样有点不合理，从用户体验工程和直觉上来说

---

## 1. 改动前的顺序，以及它为什么不直觉

```
概览 | 服务商 | 模型目录 | 网络 | 成本中心 | 请求日志 | 设置 | 访问密钥
```

逐页核过它们**实际干什么**（`PageHeader` 的 description 是权威）：

| 页 | 干什么 |
|---|---|
| 概览 | 首页：实时状态与今日用量 |
| 服务商 | 「协议、地址、鉴权与透传，以及挂载在它下面的凭据」 |
| 模型目录 | 对外暴露哪些模型 |
| 网络 | 「订阅与线路：订阅源、线路类型、节点来源、健康样本」 |
| 成本中心 | 「用量与花费的趋势和明细」 |
| 请求日志 | 「查一次请求走过了什么」 |
| 设置 | 端口 / 自启 / 托盘 / 存储 |
| 访问密钥 | 「**客户端拿这些密钥调用本机网关**」 |

问题不在"某两页挨着"，而在**语义被打断了**：

1. **配置链的终点被丢在最后。** 访问密钥是**整条配置动作的终点** —— 前面三项
   （服务商 / 模型 / 网络）都是为了让"客户端能调我"成立。它排在 `设置` **之后**，
   读起来像设置的子项。
2. **于是整条顺序的语义是**：`配置(3) → 观察(2) → 系统(1) → 又回到配置(1)`。
   最后那一项就是"不直觉"的根源 —— 一条链被切成了两半。
3. **结构完全看不见。** 8 项平铺，没有任何东西说明"这几项是一类"，
   用户只能从位置上猜；猜错了也没有反馈。

## 2. 一条被推翻的旧规则

`routes.ts` 原本写着：

> 路由表。**顺序 = 侧边栏顺序**（按使用频率，见 [05 §2]）。

**"按使用频率排"本身是反模式**，这一轮明确放弃它：

* **频率会变，位置不该变。** 今天是"服务商"，下周可能变成"日志"。
  位置一旦跟着频率漂，用户的**肌肉记忆就作废** —— 而那正是位置唯一的价值。
* **频率无法从仓库里确定。** 没有埋点、没有真实用户数据，"哪个更常用"是**猜**的。
  一条靠猜的排序规则，每次有人改它都无法被证伪。
* **位置要可预测。** 依据必须是"这一项在用户的**动作链条**里处于哪一步"——
  那是稳定的，而且**可以从每页的职责里读出来**（下一节就是这么推的）。

旧 [05 §2] 那张表还列着 10 项（含早已删除的「凭据与套餐」「通道矩阵」「路由策略」），
它描述的不是现状；本文是**现行**依据。

## 3. 新顺序：按任务流

```
概览                                 ← 先看现在怎么样（不归组，永远第一项）
── 配置 ──
   服务商 → 模型目录 → 网络 → 访问密钥   ← 接谁 → 提供什么 → 怎么出网 → 谁可以调用
── 记录 ──
   请求日志 → 成本中心                 ← 明细 → 聚合
── 系统 ──
   设置                               ← 永远最后
```

四条依据，逐条对应上面 §1 的三个毛病：

1. **按任务流排，不按频率排** —— 位置可预测（见 §2）。
2. **配置链连续、以终点收尾** —— 访问密钥跟在 `网络` 后面，不再像设置的子项。
3. **观察项相邻** —— 请求日志与成本中心是一类，不再被别类切开。
4. **设置永远最后** —— 全局通行约定；它也是唯一"改了会影响整个软件"的一页。

### 唯一真正五五开的一处：「请求日志」与「成本中心」谁在前

选**日志在前**，两个理由：

* **排查比看账单更高频** —— 出问题时第一反应是"刚才那次请求怎么了"，不是"这个月花了多少"；
* **明细 → 聚合**符合阅读方向 —— 先看清那一次，再看合起来。

这一处**已经问过用户并得到确认**，不是我自己拍的。

## 4. 分组是**数据**，不是 Sidebar 里的 if

`AppRoute` 增加可选字段 `navGroup`（i18n 键），分组顺序显式写在 `NAV_GROUP_ORDER`：

```ts
export const NAV_GROUP_ORDER: readonly I18nKey[] = [
  "navGroup.setup",     // 配置
  "navGroup.records",   // 记录
  "navGroup.system",    // 系统
];
```

**为什么单独列一遍顺序**，而不是"谁先被写进数组谁在前"：分组顺序是**设计决定**，
不该由"插入位置"顺带决定 —— 有人往中间插一项就可能把整组挪位。

`navSections()` 把它切成 Sidebar 要画的那几段，并且**在两种情况下返回 `null`**：

| 情况 | 为什么要这么严 |
|---|---|
| 同一组的项**不连续** | 否则侧边栏会画出**两个同名组**——那正是分组要消灭的东西 |
| 有项带着**没登记**的组名 | 否则那一组会静默消失，用户少看到几项且没有任何提示 |

`Sidebar` 对 `null` 的处置是**兜底成一份不分组清单**：宁可少画几条线，
也不能因为分组算不出来就**整条侧边栏空白**（那是把内部错误变成用户看不见导航）。

## 5. 视觉：细线 + 小标题，**折叠态不画标题**

* 组与组之间一条 `Divider`（1px），不是大留白 —— [15 §3.3] 的间距刻度里
  `mt` 最大只能给 24px，同屏也给不出更大的间距，而一条线比留白更明确。
* 组名用 `typography.size.label`(11px) + `letterSpacing.label` + `text.secondary`
  + `textTransform: uppercase`：**令牌内的层级差**，不引入新字号（[15 §4]）。
* **第一条（概览）不加线** —— 它上面已经是品牌区的分隔线，两条挨着会显得像两段。
* **折叠态（56px）不画组名** —— 一个字都放不下，硬塞会把图标挤歪；
  折叠态的识别靠 `Tooltip`（原本就有），不受影响。

字重只用 `medium`(500)：[15 §4.2] 规定字重只有 400/500，
`design.guard.test.ts` 的守卫 4 会拒绝 ≥600。

## 6. 验证

| 门 | 结果 |
|---|---|
| `npx tsc --noEmit` | 0 错 |
| `npx vitest run` | **609 passed / 34 files**（上一轮 605；本轮 +4 条） |

新增的 4 条（都在 `src/app/routes.test.tsx` 的「[docs/56] 侧边栏顺序与分组」下）：

1. **顺序**：`NAV_ROUTES` 的 key 序列逐一列出 —— 有人挪动任何一项都会红；
2. **分组**：首页不归组、三组按序、组名都在 zh-CN 里、**组名与项名不许撞**
   （"配置 / 配置"读起来像 bug）；
3. **连续性**：用**独立方式**再算一遍分组序列有没有回摆
   （两边都算 = `navSections` 的判定写松了这条仍会红）；
4. **真的画出来**：渲染 `AppShell`，断言侧边栏里**确实有三个组名**，
   且 DOM 文本流里 概览 < 配置 < 服务商 < 访问密钥 < 记录 < 日志 < 成本 < 系统。
   算对了但没画 = 用户还是看不到结构，所以这一条单独存在。

## 7. 本轮**没有**做的事

* **没有**改任何页面的 URL、权限、归属（`owner` 字段一个都没动）。
* **没有**增删任何一行导航项（8 项进、8 项出）—— 只改顺序与分组。
* **没有**把分组做成可折叠的树：8 项的规模下，折叠只会**多一次点击**而没有收益。
  真到二十几项、需要折叠时再说，那时 `navSections()` 已经是现成的切分点。
* **没有**改 `/` 的重定向目标（仍是 `/dashboard`）。
