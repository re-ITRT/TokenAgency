# docs/58：线路由服务商决定 —— 删掉手动建线路，修好「选不到节点」

用户第 325 轮原话（两条，附两张截图）：

> 这个功能好像没有什么用，可以在界面上删了

（截的是 `/network` 线路区块的「添加线路」按钮）

> 我已经添加了订阅和节点，但是在服务商那边选节点还是啥也没看到，这里不应该显示所有已经
> 添加的节点和"直连"，"自动选择:xx订阅"（可以有不同的订阅，多个订阅内部自动选）

（截的是服务商详情页的「网络代理」下拉，里面只有「自动 / 直连（本机网络）/ 未指定」）

这两件事其实是**同一件事的两面**：线路不该由人手工建，而该由"在服务商页选一个出口"这件事
自动产生。

---

## 1. 删掉手动建线路的界面

`/network` 线路区块的「添加线路」按钮、行内「编辑」、以及那个 `LaneWriteDialog`
（含它专用的 `LaneDraft` / `laneMissingField` / `lanePayload` / `laneDraftFromRow` /
`laneEditPayload`）**整块删除**。

**为什么它不是"少个入口"而是"少一份真相源"**：线路的三种建法各有一条后端命令 ——

| 用户选什么 | 谁来建那条线路 |
|---|---|
| 「自动」 | `provider_upsert` → `ensure_auto_lane`（id 带**服务商**，名字带服务商名） |
| 某个节点 | `lane_ensure_for_node`（id 由订阅 + 节点 slug 派生，幂等复用） |
| 「直连」 | `provider_upsert` → `ensure_direct_lane` |

留着手工表单 = 同一件事有两个入口、两套校验（`missing_kind_field` 在前端再镜像一份）、
两个可能写坏的载荷构造器。删掉之后，"这条线路该长什么样"只有后端一处判断。

线路区块保留**只读 + 行级动作**：看清单、逐条测速、删除。空态改成**指出去哪儿建**：

> 还没有线路。这里不用手建：到服务商页把「网络代理」选成「自动」/ 某个节点 / 「直连」，
> 线路会自动建出来并出现在这里。

（不改这句的话，删掉按钮就留下一条**走不通的死路**。）

---

## 2. 真正的 bug：下拉接错了数据源

### 病根

服务商详情页与添加向导的「网络代理」下拉，**两个都**从 `lane_list` 取选项。
而 `lane_list` 返回的是**已配置的线路** —— 用户刚配好的订阅节点**一条都不在里面**
（节点还没有对应的线路，要等他"选中"才会被建出来）。

仓库里其实**早就有**正确的那条路：

* 后端 `compute_lane_choices` → 命令 **`lane_options`**：直连（第一组）+ 每份订阅一组
  （该订阅下已配置的线路 **+ 已采纳版本里的每个节点**）；
* 前端 `src/pages/providers/model.ts` 的 **`proxyChoices()`**：把那些分组映射成下拉选项，
  还处理了去重（一个节点已有等价线路时只留线路那项）与分组名后缀；
* `api.lane.options()` / `lane.ensureForNode()` 也都在。

**但它们一个都没有被页面调用过。** 于是一个功能完整、有单测的能力，在真机上从来没有生效 ——
用户看到的就是"我加了订阅和节点，这里啥也没有"。

### 修法

1. 两个下拉改成读 **`lane_options`**（各自用独立 query key：`[...qk.lanes, "options"]`，
   与"已配置线路"那份分开，否则 TanStack Query 会把它们当成同一份数据互相覆盖）；
2. `providerLaneChoices` 的第一个参数从 `LaneOption[]` 换成 **`LaneChoiceGroup[]`**，
   内部先给"每份订阅一个「自动」"，再接 `proxyChoices(...)`；
3. **「自动」的标签一律带订阅名**（`自动（机场 A）`）。原来只在"多于一份订阅"时才带，
   用户看不出用的哪份 —— 而他原话就是要把订阅名写出来；
4. 保存时**先把选中的值解析成真实 lane id**。

### 第 4 条是必须的，不是锦上添花

三种值后端自己认识，**原样发**即可：`""`（继承）、`auto:<订阅>`、`direct:`。
**只有节点项不行**：它的值是 `node:<订阅>:<节点名>`，而 `provider_upsert` 只解析
`auto:` / `direct:` 两种前缀。直接发出去，后端会拿它当线路 id → 校验器报"线路不存在"
→ **用户选了节点，保存后什么都没发生**。

所以新增 `resolveLaneChoice()`（`editor.ts`）：节点项先调 `lane_ensure_for_node` 换成真实 id
（已有等价线路就直接用返回的 `lane_id`，一次都不多调）；拿不到 `nodeRef` 时**不猜**，
原样返回让后端如实报错。

## 3. 顺带修掉的一个显示错误

真机截图里第一版修完显示成 **「直连（直连（本机网络））」** —— 双括号。
原因：配置里那条 direct 线路名叫「直连」，而它的分组叫「直连（本机网络）」，
`proxyChoices` 的"分组名后缀"逻辑把它拼了一次。

修法：**「直连」那一项一律不拼分组名** —— 它是单独一项，分组名对它没有任何区分作用。
