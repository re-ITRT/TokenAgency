# 13 · 团队、权责与交付流程

> 我是这个项目的**技术主管兼产品经理**：定方向、划边界、做评审、对最终质量负责。
> 子 agent 是**团队成员**：各自拥有明确的文件范围与完成定义，独立交付，接受评审并对自己的模块负责。
>
> 本文是团队运作规则，不是产品需求。产品需求见 [README](../README.md) 与 [09 架构设计](09-architecture-design.md)。

---

# 1. 编制与权责

## 1.1 编制上限：**同时最多 5 名员工**

这是硬约束。踩过的坑：第一波按 7 个包并行派发，其中 3 个人挤在同一个 `ta-core` crate 里 —— 抢 `Cargo.toml`、抢 cargo 构建锁、边界靠人工盯。**超过 5 个人，我的评审带宽就是瓶颈，反而更慢。**

由此定下三条：

| 规则 | 说明 |
|---|---|
| 一包一人、一人一域 | 每个 crate 只有一个 Owner，不再切碎 |
| 契约先冻结再并行 | 接口冻结是并行的前提（W0 已把全部类型与 trait 定完） |
| 主岗 + 副岗 | 主岗长期不变（积累上下文 = 培养），副岗在主岗交付后顶上 |

## 1.2 固定 5 人（长期名册）

| 员工 | 主岗 | 独占文件范围 | 副岗 |
|---|---|---|---|
| **E1 领域官** | 领域与配置 | `crates/ta-core/src/{domain,config}/**` | 前端外壳 F1 |
| **E2 决策官** | 决策与账本 | `crates/ta-core/src/{routing,sticky,quota,pricing,metering}/**` | 前端 看板+日志 F2 |
| **E3 数据官** | 数据与密钥 | `crates/ta-store/**`、`crates/ta-secrets/**` | 前端 配置类页面 F3 |
| **E4 网络官** | 网络接入 | `crates/ta-kernel/**`、`crates/ta-subscription/**` | 前端 网络+成本 F4 |
| **E5 网关官** | 网关（关键路径 Owner） | `crates/ta-gateway/**` | Tauri 层 T1+T2 |
| 技术主管 | 根配置、契约文档、集成、打包 | 根 `Cargo.toml`、`docs/**`、`scripts/**`、`src-tauri`/`src` 的骨架 | — |

一人一层，正好对应架构的依赖方向（[09 §3.3](09-architecture-design.md)），**边界天然不重叠**，这是把协作成本压到最低的分法。

## 1.3 一句话规则

> **每个文件在任何时刻只有一个 Owner。没有 Owner 的归我。**

**升级路径**：员工需要改别人的文件 → **停下来报告给我**，由我决定是改契约（更新 [10](10-interface-spec.md)/[11](11-internal-contracts.md)）还是指派 Owner 处理。**严禁越界修改或复制粘贴别人的代码。**

## 1.4 首批 7 人的收敛计划

第一批超编派发了 7 个包，交付后按 `docs/12 §1.4` 收敛：留任 4 人转 E1–E4，新增 1 人任 E5（网关），**P3 / P6 / P7 转机动岗**（内核真机 spike、golden 快照补强、不变量自检脚本），用完即回收。

# 2. 员工的"入职材料"（每包必读）

派发任务时固定给这几样，缺一不可 —— 这是让员工独立干活的必要条件，不是可选项：

1. **要读的文档清单**（含章节号，不要让人自己翻）
2. **独占文件范围**（能写什么）
3. **冻结契约**（不能改什么：类型名、trait 签名、错误码、字段名）
4. **要做的事**（编号列表，具体到函数/规则）
5. **完成定义（DoD）**（可执行、可判定，通常是一条命令 + 测试覆盖清单）
6. **汇报格式**（改了哪些文件 / 验证命令结论 / 遗留问题与不确定点）

# 3. 评审协议（我会做的四件事）

员工交付 ≠ 完成。每个工作包交回来，我按下面四层评审：

| 层 | 看什么 | 不合格怎么处理 |
|---|---|---|
| **L1 边界** | 有没有越界改别人的文件？有没有偷偷改契约？ | 直接打回，要求说明原因并改回 |
| **L2 门禁** | `cargo fmt --check` / `clippy -D warnings` / `cargo test -p <crate>` 是否真绿 | 打回，贴出门禁输出 |
| **L3 契约符合度** | 对照 [10]/[11] 逐条核对：字段名、错误码、节流规则、事务边界、硬约束（如"图片只存哈希"、"cached 必须先减掉"） | **带着具体行号发回给原员工**，不自己改 |
| **L4 工程质量** | 有没有 `todo!()` 占位？测试是不是真断言（而不是 `assert!(true)`）？有没有把复杂度藏进 `unwrap()`？命名与注释是否解释了"为什么"？ | 写评审意见发回，给改进方向而不是替他写 |

**评审意见的写法**（培养的关键）：不说"这里不对"，要说 **现象 → 为什么是问题 → 期望的样子 → 验收方式**。员工保留上下文，能自己改对。

# 4. 培养机制（长期）

| 机制 | 做法 |
|---|---|
| **一次说清** | 派发时给足上下文（文档章节 + 契约 + DoD），减少返工。返工的成本远高于写清楚的成本 |
| **原地反馈** | 发现问题**发回给原员工**（它保有上下文），而不是我自己动手改。只有"契约本身错了"才由我改 |
| **模式化升级** | **如果 2 个以上员工犯同一个错 → 这是契约/文档的问题，不是员工的问题。** 我去改 [11] 或示例代码，然后广播给所有人。这是团队学习，不是逐个纠错 |
| **留下范本** | 第一个把某类事做对的员工，其代码作为后续同类的参照（如 G1 的全透传实现会是 G3 的范本） |
| **明确禁区** | 安全（密钥、图片 base64）、不变量（系统网络零副作用、全透传）、计费正确性（cached 必须减）—— 这三类零容忍，没有"先这样后面再改" |

# 5. 产品经理视角：验收的唯一标准

功能多少不是标准。**用户最初列的痛点是否真的消失**才是：

| 优先级 | 用户痛点 | 验收方式 |
|---|---|---|
| P0 | 换套餐要改客户端配置 | 只改一次 base_url 后，后续换套餐/换 key 全程不动客户端 |
| P0 | 多个套餐映射同一模型不会自动切换 | 打满 A 家额度 → 自动切 B → 同会话后续保持 B |
| P0 | 代理吞掉视觉能力 / agent 标识 | golden 快照：图片块与自定义头逐字节到达上游 |
| P0 | 每条线路要能独立指定且不碰系统网络 | 两个模型指向不同线路，`curl` 出口 IP 不同；启停前后系统代理/路由/DNS 快照一致 |
| P1 | 没有托盘、只能开网页 | 托盘右键两下内切策略/切节点/看额度 |
| P1 | 用了多少 token、花了多少钱看不清 | 成本中心按"套餐 × 时间 × token 类型"任意组合查询 |
| P2 | 已有 Clash 订阅要重配 | 导入订阅后分组名直接可选为线路 |

**范围纪律**：任何超出上表的"顺手也做了"的提案，默认进 backlog 不进本轮。本轮目标是**跑通 M1 并出安装包**。

# 7. 已知的团队级约束

| 约束 | 说明 |
|---|---|
| **编制上限 5 人** | 同时最多 5 名员工。超了，我的评审带宽就是瓶颈 |
| **并发写冲突** | 同一 crate 的多个员工共用 `Cargo.toml`。规则：**该文件冻结**，缺依赖要报告，由我统一加 |
| **cargo 锁竞争** | 多人同时 `cargo test` 会串行等待（正常现象，不是故障）。验收时允许等待 |
| **契约冻结期** | W1–W2 期间 [10]/[11] 不改；确需变更必须由我改文档并广播 |
| **交付即测试** | 员工不得交付"能编译但没测试"的模块；也不得用 `#[ignore]` 藏测试 |
