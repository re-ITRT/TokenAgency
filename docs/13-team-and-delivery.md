# 13 · 团队、权责与交付流程

> 我是这个项目的**技术主管兼产品经理**：定方向、划边界、做评审、对最终质量负责。
> 子 agent 是**团队成员**：各自拥有明确的文件范围与完成定义，独立交付，接受评审并对自己的模块负责。
>
> 本文是团队运作规则，不是产品需求。产品需求见 [README](../README.md) 与 [09 架构设计](09-architecture-design.md)。

---

# 1. 编制与权责

## 1.1 编制上限：**同时最多 5 名员工**

这是硬约束。踩过的坑：第一波按 7 个包并行派发，其中 3 个人挤在同一个 `ta-core` crate 里 —— 抢 `Cargo.toml`、抢 cargo 构建锁、边界靠人工盯。**超过 5 个人，我的评审带宽就是瓶颈，反而更慢。**

由此定下三条：

| 规则 | 说明 |
|---|---|
| 一包一人、一人一域 | 每个 crate 只有一个 Owner，不再切碎 |
| 契约先冻结再并行 | 接口冻结是并行的前提（W0 已把全部类型与 trait 定完） |
| 主岗 + 副岗 | 主岗长期不变（积累上下文 = 培养），副岗在主岗交付后顶上 |

## 1.2 固定 5 人（长期名册）

> **第 11 轮按实际运行状态校正过一次**：原表把 `src-tauri` 放在 E5 的副岗，但 T1/T2 全在
> `src-tauri`，与 `ta-store` 同属"数据 → 桌面"一条链 —— 交给两个人必然在同一个目录里抢文件
> （[docs/12 §1.1] 的纪律）。现改为 E3 独占 `src-tauri`，E5 专心守关键路径网关。
> **实例名**一栏是 `send_message` 用的地址；员工长期在位、不换岗，上下文持续累积。

| 员工（岗位） | 主岗 | 独占文件范围 | 实例名 |
|---|---|---|---|
| **E1 前端与领域官** | 前端 + 领域与配置 | `src/**`、`crates/ta-core/src/{domain,config}/**` | `e1-ui` |
| **E2 决策与可观测官** | 决策/账本 + 可观测 | `crates/ta-core/src/{routing,sticky,quota,pricing,metering}/**`、`crates/ta-core/src/diag/**` | `e2-decision` |
| **E3 数据与桌面官** | 数据/密钥 + 桌面层 T1/T2 | `crates/ta-store/**`、`crates/ta-secrets/**`、`src-tauri/**` | `e3-desktop` |
| **E4 网络官** | 网络接入（内核 + 订阅） | `crates/ta-kernel/**`、`crates/ta-subscription/**` | `e4-network` |
| **E5 网关官** | 网关（关键路径 Owner） | `crates/ta-gateway/**` | `e5-gateway` |
| 技术主管 | 契约文档、集成、打包、门禁 | 根 `Cargo.toml`、`docs/**`、`scripts/**`、`.githooks/**` | `lead` |

> ⚠️ **上表是"可读版本"，不是权威定义。** 独占文件范围的权威定义在
> `scripts/commit.ps1` 的 `$Scopes` —— 那是**机械执行**的检查（越界直接拒绝提交）。
> 两处不一致时以 `$Scopes` 为准，并立刻改这张表。
> 第 11 轮就是因为两处不一致（前端路径挂在 E5 名下、E3 没有 `src-tauri`），
> 让 E1 **每提交一次前端都要走 `-Override`** —— 一条真实的流程摩擦，
> 由 E1 主动发现并报上来（[§8.6](#86-第-11-轮--agent-team-重开在岗名册与派工)）。

一人一层，正好对应架构的依赖方向（[09 §3.3](09-architecture-design.md)），**边界天然不重叠**，这是把协作成本压到最低的分法。

## 1.3 一句话规则

> **每个文件在任何时刻只有一个 Owner。没有 Owner 的归我。**

**升级路径**：员工需要改别人的文件 → **停下来报告给我**，由我决定是改契约（更新 [10](10-interface-spec.md)/[11](11-internal-contracts.md)）还是指派 Owner 处理。**严禁越界修改或复制粘贴别人的代码。**

## 1.4 首批 7 人的收敛计划

第一批超编派发了 7 个包，交付后按 `docs/12 §1.4` 收敛：留任 4 人转 E1–E4，新增 1 人任 E5（网关），**P3 / P6 / P7 转机动岗**（内核真机 spike、golden 快照补强、不变量自检脚本），用完即回收。

# 2. 员工的"入职材料"（每包必读）

派发任务时固定给这几样，缺一不可 —— 这是让员工独立干活的必要条件，不是可选项：

1. **要读的文档清单**（含章节号，不要让人自己翻）
2. **独占文件范围**（能写什么）
3. **冻结契约**（不能改什么：类型名、trait 签名、错误码、字段名）
4. **要做的事**（编号列表，具体到函数/规则）
5. **完成定义（DoD）**（可执行、可判定，通常是一条命令 + 测试覆盖清单）
6. **汇报格式**（改了哪些文件 / 验证命令结论 / 遗留问题与不确定点）

# 3. 评审协议（我会做的四件事）

员工交付 ≠ 完成。每个工作包交回来，我按下面四层评审：

| 层 | 看什么 | 不合格怎么处理 |
|---|---|---|
| **L1 边界** | 有没有越界改别人的文件？有没有偷偷改契约？ | 直接打回，要求说明原因并改回 |
| **L2 门禁** | `cargo fmt --check` / `clippy -D warnings` / `cargo test -p <crate>` 是否真绿 | 打回，贴出门禁输出 |
| **L3 契约符合度** | 对照 [10]/[11] 逐条核对：字段名、错误码、节流规则、事务边界、硬约束（如"图片只存哈希"、"cached 必须先减掉"） | **带着具体行号发回给原员工**，不自己改 |
| **L4 工程质量** | 有没有 `todo!()` 占位？测试是不是真断言（而不是 `assert!(true)`）？有没有把复杂度藏进 `unwrap()`？命名与注释是否解释了"为什么"？ | 写评审意见发回，给改进方向而不是替他写 |

**评审意见的写法**（培养的关键）：不说"这里不对"，要说 **现象 → 为什么是问题 → 期望的样子 → 验收方式**。员工保留上下文，能自己改对。

# 3.5 交付前自检清单（员工必填）

**这不是给我看的报告，是给员工自己的护栏。** 交回来时按这个模板回，缺项直接打回重填——不是我要求高，是这些项每一条都对应过真实事故。

## A. 边界（越界即作废）

- [ ] 我只改了派发时指定的文件范围；`git status` 里没有我的范围外改动
- [ ] 我没有修改 `docs/**`、根 `Cargo.toml`、`crates/*/Cargo.toml`
- [ ] 我没有删改已有公开类型的字段名或 trait 签名
- [ ] 如果需要改别人的文件，我是**报告**的，不是自己动的

## B. 门禁（贴真实输出，不许写"通过了"）

- [ ] `cargo fmt --all -- --check` → 贴退出码
- [ ] `cargo clippy -p <crate> --all-targets -- -D warnings` → 贴退出码
- [ ] `cargo test -p <crate>` → **贴测试数量与结果**（如 `12 passed; 0 failed`）
- [ ] `cargo check --workspace` 仍然绿

## C. 反模式自查（这是"干净产出"的核心）

- [ ] **没有** `todo!()` / `unimplemented!()` / `unreachable!()` 当占位交付
- [ ] **没有** `#[ignore]` 藏测试
- [ ] **没有** 假测试：`assert!(true)`、只调用不判言、只测 `is_ok()` 而不看值
- [ ] **没有** 在非测试代码里对可失败路径直接 `unwrap()` / `expect()`
- [ ] **没有** 用 `as` 做可能截断的数值转换（金额、token 数一律用 `f64`/`u64` 显式转换）
- [ ] 注释解释的是**为什么**，不是复述代码在做什么
- [ ] 函数里没有"顺手也做了"的无关改动

## D. 本项目的硬约束（零容忍，逐条确认）

- [ ] 计费：`cached` 已从 input 总数里**减掉**，`reasoning`/`audio` 已从 output 里**减掉**
- [ ] 安全：图片只存 `{type, media_type, bytes, sha256_prefix}`，**没有任何 base64 落库**
- [ ] 安全：**key 绝不进数据库、绝不进日志、绝不进 trace**
- [ ] 网络：**没有任何**系统代理 / 路由表 / TUN / DNS / 防火墙操作
- [ ] 透传：没有用 `#[derive(Deserialize)]` 定义请求体结构（会静默吞字段）
- [ ] 事务：一次请求的账本写入在**单事务**内

## E. 遗留与不确定（必须诚实填，写"无"也要写）

- [ ] 我没做、但契约里要求了的东西（列出来）
- [ ] 我不确定、需要主管裁决的设计点（列出来）
- [ ] 我发现但没权限改的别人的问题（列出来，我来路由）

> **"不确定"写出来是加分项。** 藏着不确定、假装做完了，才是真的失职 —— 它会在集成阶段以十倍成本爆出来。

# 4. 培养机制（长期）

| 机制 | 做法 |
|---|---|
| **一次说清** | 派发时给足上下文（文档章节 + 契约 + DoD），减少返工。返工的成本远高于写清楚的成本 |
| **原地反馈** | 发现问题**发回给原员工**（它保有上下文），而不是我自己动手改。只有"契约本身错了"才由我改 |
| **模式化升级** | **如果 2 个以上员工犯同一个错 → 这是契约/文档的问题，不是员工的问题。** 我去改 [11] 或示例代码，然后广播给所有人。这是团队学习，不是逐个纠错 |
| **留下范本** | 第一个把某类事做对的员工，其代码作为后续同类的参照（如 G1 的全透传实现会是 G3 的范本） |
| **明确禁区** | 安全（密钥、图片 base64）、不变量（系统网络零副作用、全透传）、计费正确性（cached 必须减）—— 这三类零容忍，没有"先这样后面再改" |
| **自检先于评审** | 用 §3.5 清单把基础质量变成员工的责任，我的评审带宽只花在真正的判断上（设计、边界、取舍） |

# 4.5 经验教训（边做边学，持续累积）

> 只记**踩过的、有代价的**。每条都对应一个具体事故，不是泛泛的道理。

| # | 教训 | 事故现场 | 已固化成什么 |
|---|---|---|---|
| L1 | **跑一次真实检查，胜过读十遍设计文档** | 不变量检查脚本把用户机器上"本来就开着的系统代理"报成违规 —— 我按直觉写了绝对断言，跑起来才发现语义错了 | I2 语义写死进 [09 §1.2](09-architecture-design.md)：**"前后一致"而非"必须是关的"**；判据只有"我们有没有改变它" |
| L2 | **接口里的"名字"必须显式对齐，不能靠推导** | `TaEvent` 序列化出 `request_new`，文档和前端写的是 `request:new`。编译全过、运行全静默，前端就是收不到消息 | 每个变体显式 `rename`，并加 `TaEvent::name()`；事件名只在 [10 §2.3](10-interface-spec.md) 一处定义 |
| L3 | **RC 阶段的依赖必须钉死精确版本** | `specta = "2"` 解析失败（只有 `2.0.0-rc.25` 这类预发布版） | 根 `Cargo.toml` 改成 `=2.0.0-rc.25` 并注明"工作包 T1 使用" |
| L4 | **配置声明与实际功能必须一致，否则是编译期硬失败** | `tauri` 开了 `protocol-asset` feature，但 `tauri.conf.json` 没有对应的 `assetProtocol` 段 → 构建脚本直接报错 | 移除该 feature；原则：manifest 与 config 改动必须成对 |
| L5 | **环境里的历史垃圾会伪装成工具 bug** | 父目录 `C:\Users\19404\workspace\package.json` 是 0 字节文件 → 先让 pnpm 报 JSON 解析失败，再让 esbuild 构建失败。看起来都像工具问题 | 处置原则：**项目外的文件不删除，只补成合法内容**（写入 `{}`）；并记录在 README 的开发说明里 |
| L6 | **并行度必须与代码边界对齐，否则是负优化** | 第一波 7 个包并行，其中 3 人挤在同一个 `ta-core` crate：共用 `Cargo.toml` 不能改、抢 cargo 构建锁、边界靠人工盯 | 编制上限 5；**一人一层**（对应架构依赖方向），主岗长期不变 + 副岗补位 |
| L7 | **干净失败远好过半成品** | P6 失败，但 `ta-subscription` 仍停在上一个可用状态，零残留 | 定损流程：先看"有没有留下编译不过的东西"，再决定是回滚还是重做。**不做无谓的救火** |
| L8 | **契约冻结是并行的前提，也是提前开工的机会** | W0 把全部 trait 定义完，于是网关（关键路径）不必等 store/kernel 实现完，可以对着 trait 先写 | 波次计划里把 E5（网关）提前到 W1；契约冻结期明确为 W1–W2 |
| L9 | **手写的示例/文档必然与代码漂移，要把它变成生成物 + 上守卫** | 员工 P1 实测抓出我手写的 `config.example.yaml` 有三处**硬错误**（`off` 在 YAML 1.2 里是字符串不是 bool、`filter` 写成 mapping、`failover.on` 用 `http_429` 而枚举是 `http429`），外加一批字段名不对——**静默落进 `extra`、运行时不生效、却完全不报错** | 示例改成 `scripts/gen-example-config.ps1` 从 `default_doc()` 生成；加 `crates/ta-core/tests/example_config_guard.rs` 三道守卫（能读通 / 无未知字段 / 序列化幂等）。**给员工建了安全网，而不是骂他们看错了文档** |
| L10 | **"不报错但不生效"比"编译失败"危险得多** | 上面那批历史字段名（`interval`/`ttl`/`cooldown`）会让用户以为配上了、实际没生效 —— 编译期和运行期都静默 | 命名纪律：带单位的字段必须带后缀（`interval_s`/`ttl_h`/`cooldown_s`/`connect_s`/`read_s`/`tolerance_ms`）；各实体的 `extra` 字段用 `semantic_eq` 做全量比对来检测未知字段 |

# 5. 产品经理视角：验收的唯一标准

功能多少不是标准。**用户最初列的痛点是否真的消失**才是：

| 优先级 | 用户痛点 | 验收方式 |
|---|---|---|
| P0 | 换套餐要改客户端配置 | 只改一次 base_url 后，后续换套餐/换 key 全程不动客户端 |
| P0 | 多个套餐映射同一模型不会自动切换 | 打满 A 家额度 → 自动切 B → 同会话后续保持 B |
| P0 | 代理吞掉视觉能力 / agent 标识 | golden 快照：图片块与自定义头逐字节到达上游 |
| P0 | 每条线路要能独立指定且不碰系统网络 | 两个模型指向不同线路，`curl` 出口 IP 不同；启停前后系统代理/路由/DNS 快照一致 |
| P1 | 没有托盘、只能开网页 | 托盘右键两下内切策略/切节点/看额度 |
| P1 | 用了多少 token、花了多少钱看不清 | 成本中心按"套餐 × 时间 × token 类型"任意组合查询 |
| P2 | 已有 Clash 订阅要重配 | 导入订阅后分组名直接可选为线路 |

**范围纪律**：任何超出上表的"顺手也做了"的提案，默认进 backlog 不进本轮。本轮目标是**跑通 M1 并出安装包**。

# 7.5 提交协议：身份 + 范围强制

> 起因是 L17 —— 主管排查"谁动了 `ta-subscription`"时只能靠文件时间戳**推断**，还推错了人。
> 不同提交身份能从根上消除这类问题：`git log --format='%an'` 直接给答案。

## 7.5.1 只能用 `scripts/commit.ps1` 提交

```powershell
pwsh -File scripts/commit.ps1 -As E4 -Paths crates/ta-subscription -MessageFile msg.txt -AgentId <你的 id>
```

| 参数 | 说明 |
|---|---|
| `-As` | 你的身份：`lead` / `E1`…`E5` / `mech` |
| `-Paths` | **只提交这些路径**。不会影响别人已暂存的内容 |
| `-Message` / `-MessageFile` | 多行中文用 `-MessageFile`（PowerShell 传多行参数不可靠） |
| `-AgentId` | agent 实例 id，写进 trailer 便于交叉核对 |
| `-Override "原因"` | 提交范围外文件时必填，写进 trailer，可审计 |

提交后会自动追加 trailer：

```
Work-Package: E4
Agent-Id: 5eebd5cb
```

## 7.5.2 范围检查是**机械的**，不是靠自觉

脚本内置了 §1.2 的编制表。E4 去提交 `docs/` 会被直接拒绝：

```
✘ 越界：以下路径不在 E4（网络接入）的范围内
    docs/06-roadmap-and-risks.md
  你的范围：
    crates/ta-kernel
    crates/ta-subscription
  确实需要提交范围外的文件时：-Override "一句话说明原因"
```

**这把"不许越界"从口头约定变成了工具约束。** 拒绝时退出码为 `2`，与"门禁未过"（`1`）区分开。

## 7.5.3 溯源：`scripts/who.ps1`

```powershell
pwsh -File scripts/who.ps1                                  # 各身份改了多少文件
pwsh -File scripts/who.ps1 -Path crates/ta-subscription     # 这个目录谁在改
pwsh -File scripts/who.ps1 -File crates/ta-core/src/types.rs # 单文件历史
pwsh -File scripts/who.ps1 -Author E4                       # 某身份改了什么
pwsh -File scripts/who.ps1 -Uncommitted                     # 在途未提交的（按范围粗归因）
```

## 7.5.4 ⚠️ 这条约定成立的前提：**勤提交**

**`git` 无法归属未提交的改动。** 如果一名员工的活儿只在工作区躺着，任何溯源工具都帮不上忙 —— 这恰恰是 L17 的场景。

所以配套要求：

> **每完成一个"可编译的里程碑"就提交一次**，让在途窗口尽量短。
>
> 具体到实践：写完一个模块能 `cargo check` 通过 → 提交；改完一组测试全绿 → 提交。
> **不要攒到最后一次性提交** —— 那样你在途期间，别人既无法溯源，也可能被你的半成品挡住（L16）。

`commit.ps1` 对 `index.lock` 竞争做了重试（最多 6 次退避），所以多人同时提交不会互相失败。

# 7.6 PR 流程：员工不再直提 master（第 11 轮，用户要求）

> 用户原话："后续的过程中可以用PR形式，你的每个员工自己fork出去，自己commit，
> 最后确认之后提PR，给你审核，越来越像真实团队。"

## 7.6.1 为什么要改

直提 master 有两个真实的痛，都发生过：

1. **在途半成品落在主干上。** E2 写 `diag` 的那段时间 ta-core 编不过，
   E4 / E5 / E3 全被挡住一轮（[L16](#45-经验教训边做边学持续累积)）。
   根因不是 E2 写得慢，而是"**在途状态**"和"**主干状态**"是同一个东西。
2. **没有评审点。** main 变成"谁的活干到哪算哪"，而不是"过审的东西"。

## 7.6.2 怎么用（员工）

```powershell
# 提 PR（可反复调用：每次往自己的分支上追加一个提交，保留里程碑粒度）
pwsh -File scripts/pr.ps1 -As E4 -Paths crates/ta-kernel -Title "B4：内核 stdout/stderr 转发进 tracing" -MessageFile msg.txt

# 看所有在提的 PR / 看某一个 PR 的完整 diff
pwsh -File scripts/pr.ps1 -List
pwsh -File scripts/pr.ps1 -Show wp/e4
```

- `-Paths` 必须落在你的独占范围内（权威定义：`scripts/_team.ps1` 的 `$Scopes`）。
  确需范围外文件：`-Override "一句话原因"`（写进 trailer，可审计）。
- 多行中文**必须**用 `-MessageFile`（PowerShell 会把多行参数切碎）。
- 提交前会跑 **`scripts/gate.ps1`** —— 与 git 钩子**同一份**检查；不过就不产生提交。
- `Cargo.lock` 是每个员工的**隐式范围**：改任何 crate 的 `Cargo.toml` 都会连带改它，
  不带上的话 PR 会并入新依赖却留下不一致的锁文件。

## 7.6.3 怎么实现的（为什么不影响并行）

关键点：**不需要第二个 worktree，也不动工作区**。

`pr.ps1` 用一个**临时 index**（`GIT_INDEX_FILE`）从基点 `read-tree`，只把该员工范围内的
改动 `git add` 进去，再 `git write-tree` + `git commit-tree` 造出提交，最后
`git update-ref refs/heads/wp/<员工>` 挪分支指针。**全程不切分支、不动 HEAD、
不动真实索引、不动工作区文件。**

所以五个员工仍在同一棵树上并行干活，而 `master` 只接收过审的东西。
分支名 `wp/<员工>` 就是身份，`git log` 直接可溯源。

> **为什么不用 worktree：** 员工的文件工具按**会话工作区根**解析相对路径。
> 给每人一个 worktree 就等于要求所有人在所有工具里改用绝对路径 ——
> 一次疏忽就会**静默**改到主树，隔离变成假象。用临时 index 拿到同样的
> "分支隔离 + 评审点"，却没有这个失败模式。**能用一个便宜机制消掉的失败模式，
> 不要用纪律去防。**

## 7.6.4 怎么评审（主管）

1. `pwsh -File scripts/pr.ps1 -Show wp/e4` —— 读 diff。
2. **门禁必须在"合并后的结果"上跑**，而不是只在 PR 分支上跑：
   PR 之间可能有接口依赖（E5 的装配函数要等 E2 的契约），
   只测单个 PR 会漏掉组合态。
3. 合并：`git merge --no-ff wp/e4`（保留 PR 边界，便于回滚）。
   注意 `git merge` **不触发 `pre-commit`**（git 只跑 `pre-merge-commit`），
   所以**主管的门禁就是唯一门禁** —— 这就是第 2 步不能省的原因。
4. 评审不通过：主管给回"现象 → 为什么是问题 → 期望 → 验收方式"，
   员工在同一条 PR 分支上追加提交（不新开分支，讨论留在原地）。
5. 合并后删除分支并保留提交信息里的 `PR-Branch:` trailer 作为溯源线索。

## 7.6.5 主管仍可直提

`scripts/commit.ps1` 只允许 `lead` / `mech` 使用（员工调用会被拒绝并提示转 `pr.ps1`）。
主管直提用于：契约文档、脚本、`.githooks`、根 `Cargo.toml`、以及**合并 PR**。

## 7.6.6 同步纪律：共享工作树里"pull 最新"是什么意思

用户问过我一句话："每次 PR 合并之后，你的下属都要去 pull 最新的，**你确定他们真的知道吗**？"
—— 我不确定，所以把它变成机械的。

我们五个人**共享同一棵工作树**（为了让文件工具的相对路径一直有效）。因此：

- **合并 PR 时 `git merge` 会立刻更新工作树里那些文件** —— 合并那一刻员工就已经是最新的，
  不需要（也没有地方）`git pull`。
- **但"文件最新"≠"他脑子里的假设最新"。** 真正的风险是：半小时前读过的函数签名、枚举变体、
  字段在 master 前进后**变了而他不知道** —— 编译可能过，逻辑却是错的。

所以每次动手前先跑 **`pwsh -File scripts/pr.ps1 -Status -As E?`**，它给出：master 到哪了 /
PR 基点落后几个提交（⚠ 会列出 **master 上落在他范围内**的文件）/ 他范围内还有多少未提交改动。

两条硬规则：

1. **看到 ⚠ 落后就重新读一遍列出的文件再动手**，不要凭记忆。
2. **提了 PR 之后不要再改同一批文件** —— 合并时要求工作树与该 PR 内容一致，否则 `git merge`
   会**拒绝**（git 宁可报错也不覆盖员工的在途工作）。要继续做下一件事，就**追加提交到同一条
   PR 分支**（再跑一次 `pr.ps1`，不加 `-Reset`）。

## 7.6.7 同行评审：指派人，而不是"有人会看"

用户建议"可以专门安排一个员工来审 PR"。对 —— 我长期当**唯一守门人**，既是我成为瓶颈，
也不该是长期形态。

**轮值映射（按"谁最可能被这个 PR 影响"定，不是随机）：**

| PR 作者 | 同行评审人 | 为什么是它 |
|---|---|---|
| E1 前端与领域 | E3 | E3 拥有 IPC 契约与事件桥接，前端消费的正是它产出的东西 |
| E2 决策与可观测 | E1 | E1 的 UI 是 E2 那些判定函数的**消费者**，最该问"这我真能用吗" |
| E3 数据与桌面 | E2 | E3 接的是 E2 定义的可观测契约，E2 最清楚接线接对没有 |
| E4 内核与订阅 | E5 | 网关是内核 `PortMap`/lane 端口的下游 |
| E5 网关 | E4 | dialer、lane 端口、内核 REST 都是 E4 的地盘 |

提 PR 时用 `-Reviewer E?`（进 trailer，`-List` 可见；不能是作者自己）。

**怎么做（不是"看一眼 approve"）**：只读、不改作者文件、不做 git 写操作；输出三栏
**A 阻塞项**（`file:line` + 问题 + 为什么 + 建议修法）/ **B 建议** / **C 已核实无问题**
（写清"核实了什么、怎么核实的"）；**结论必须有 `file:line` 证据**，不确定写"无法判断"。
四件必查：**不变量**（I1/I2/I3）、**密钥明文**、**日志契约**（字段白名单 + 报 `TaError`
必带 `code =`）、**测试是否真在断言**（守卫要先证明会失败）。

**效果已经验证**：`wp/e5` 的"配置换代同代窗口"被**两条独立路径**同时发现（主评审员 + E4 的
同行评审），证据链完全一致。**两条独立路径指向同一个 bug，比一个人说十遍更有说服力** ——
这就是同行评审要买的东西。

## 7.6.8 跨范围保护：`-Paths` 是 pathspec，不是文件清单

> **真实事故（我犯的）**：用 `-Paths docs,crates/ta-core` 提交契约改动时，`crates/ta-core`
> 是**目录**，于是把 E2 在途的 201 行 quota/metering 一起卷了进来 —— 提交信息写的是
> `docs(observability)`、署名是主管，而 E2 的 PR 当场变成"无可提内容"。
> **归属、信息、评审点三样全错。**

`commit.ps1` 现在做机械检查：主管提交时，只要待提交文件落在**别人独占范围**里，就必须显式
`-Override "原因"`，否则拒绝（exit 3）并直接提示"常见成因：`-Paths` 传的是**目录**"。

契约文件（如 `docs/14 §5.6` 与 `diag/fields.rs` 必须同改）会命中这条 —— 那就堂堂正正写理由，
这正是它存在的意义。

**顺带一条**：`Cargo.lock` 是每个员工的隐式范围，但**只在"你自己动了某个 `Cargo.toml`"时**
才自动带上。无条件带上会把别人在途的依赖变更捎进你的 PR（实测发生过两次：E2 与 E5 的 PR 里
都夹带了 E4 在途 `ta-kernel/Cargo.toml` 造成的锁文件变更）。
