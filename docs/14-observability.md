# 14 · 日志、错误追踪与诊断

> **这一份是"能查到问题"的基础设施契约。** 它不增加功能，它决定**出了问题我们能不能查**。
> 先写它再做别的，是因为后面每写一行代码都需要它 —— 等写到一半再补，就得回头改所有调用点。
>
> **与 [07 §2] 的分工**：[07 §2] 管的是**请求日志**（每次 LLM 请求一行，**入 SQLite**，供看板/成本中心/日志页查询）。
> 本文管的是**应用日志**（进程运行轨迹，**落文件**，供排查故障）。两者是**两件不同的东西**，
> 服务于不同的问题，不要合并 —— 详见 §1.2。

---

# 1. 为什么要做（先看清现状的四个洞）

现在项目里**已经有 101 处 `tracing` 调用**，字段结构化、注释认真，基础比预期的好。
问题不在"没人打日志"，在下面四件事：

## 1.1 洞一：日志**没有落点** —— 托盘应用根本没有控制台

`src-tauri/src/lib.rs` 的 `init_tracing()` 只挂了一个写 **stdout** 的 fmt layer。

**但这是一个托盘应用。** 用户从开始菜单启动它时 **stdout 指向虚空** ——
没有控制台窗口，日志写进去就没了。**线上出问题时，我们和用户都无处可看。**

> 顺带一个隐患：`src-tauri/src/plugins.rs` 还注册了 `tauri_plugin_log`，
> 与 `tracing_subscriber` **是两套并行的日志系统**，各自决定日志去哪。**这本身就是"日志不可预测"的原因。**

## 1.2 洞二：**错误码在日志里丢失** —— 无法按 TA 码检索

`TaError` 的 `Display`（`thiserror`）只输出**中文文案**：

```
tracing::warn!(error = %e, "订阅下载失败")
   →  订阅下载失败 error=凭据无效或已被封禁：cmd-code
```

**`TA-4001` 这个码根本没出现在日志里。** 而 [11 §5] 那张错误码总表才是**故障索引** ——
运维/排查的第一步就是"搜这个码，看所有相关日志"。现在这一步做不到。

> **这是本次改动最核心的一条**：不是"多打点日志"，是**让每条错误日志都能被码检索到**。

## 1.3 洞三：没有**关联 ID 约定** —— 一条请求的轨迹散在各处

一次请求会穿过 `ingress → pipeline → routing → kernel → dispatch → meter → trace`，
中途还会分叉到**后台任务**（内核看护、订阅同步、额度落库）。
现在各处只记自己知道的字段，**同一件事在不同日志行里用的是不同的键名**（有的 `sub`、有的 `subscription`、有的 `subscription_id`）。

**后果**：想回答"这次失败请求到底走了哪条 lane、第几次尝试才失败"，
要人肉把几条时间相近的日志拼起来 —— 而并行请求一多就拼不出来了。

## 1.4 洞四：**没有脱敏层** —— 日志是最容易泄密的地方

`ta-secrets` 做得很对（`SecretString` 的 Debug/Display 默认脱敏），请求日志也有 4 道脱敏闸。
**但应用日志这一路没有。** 任何一句 `tracing::debug!("url={url}")` 都可能把
带 `?key=sk-...` 的 URL 原样写进一个**用户随手就能发给他人的文件**里。

而诊断包（§7）的设计前提正是"**用户可以放心把它发出去**"。

# 2. 目标与非目标

## 2.1 目标

| # | 目标 | 判据（可测） |
|---|---|---|
| **G1** | 出了问题**查得到** | 日志文件存在于确定路径；用户能一键打开；`scripts/logs.ps1` 可实时跟随 |
| **G2** | 能追**一条请求的全生命周期** | 拿一个 `request_id` 能筛出它经过的**全部**日志行，含跨 crate 与后台分叉 |
| **G3** | 错误带**可操作上下文** | 每条错误日志都能 grep 到 `TA-xxxx`，并带定位所需字段（哪一步/哪个通道/第几次尝试） |
| **G4** | **永不泄露密钥** | 有自动化测试：喂进已知形态的假密钥，输出里搜不到 |
| **G5** | 用户能**交出一份诊断包** | 界面上一次点击；解压后不含任何密钥（自动化测试保证） |
| **G6** | 日志**自身不成为新问题** | 写盘不阻塞请求；磁盘满/写失败不 panic；有丢失计数 |

## 2.2 非目标（明确不做，避免范围蔓延）

- ❌ **不引入 OpenTelemetry / 分布式追踪后端**。这是单机个人应用，OTLP exporter 是纯负担。
- ❌ **不做日志上报/遥测**。"一个人的中转站"不该有任何回传 —— 用户的数据不出本机。
- ❌ **不把应用日志写进 SQLite**。理由见 §1.2 结尾与 §9.3：写库失败会产生日志、日志又要写库，是个递归；
  且日志量远大于请求日志，会把库撑爆。**文件是应用日志的唯一真相源。**
- ❌ **不做结构化日志的远程聚合**。

# 3. 不做架构改动（这是关键约束）

**`tracing` 已经是全项目的日志门面，101 处调用点不必改。** 本次只补四样东西：

| 补什么 | 放哪 | 为什么放这 |
|---|---|---|
| **落点**：文件 + 轮转 + 非阻塞写 | `src-tauri/src/logging.rs` | 只有应用层知道"日志该放用户的哪个目录"；IO 不该下沉到领域层 |
| **脱敏层**：规则 + 格式化时改写 | `crates/ta-core/src/diag/` | `ta-core` 已经在用 `tracing`（硬约束允许），且脱敏规则要被 **trace 与 log 两路复用** |
| **关联约定**：字段名表（§5） | 本文 + `diag` 里的常量 | 这是**人的约定**，不是代码；但可用一条守卫测试机械检查 |
| **诊断包**：导出 | `src-tauri/src/logging.rs` + `commands/` | 要读配置、系统信息、日志文件，都在应用层 |

**不新增 crate。** 理由：各 crate 早已直接依赖 `tracing`，没有"门面"要封装；
新增 crate 只会增加依赖层级而不解决任何问题。

# 4. 日志落点与轮转

## 4.1 路径（按平台惯例，让用户找得到）

| 平台 | 目录 |
|---|---|
| Windows | `%LOCALAPPDATA%\TokenAgency\logs\` |
| macOS | `~/Library/Logs/TokenAgency/` |
| Linux | `~/.local/state/tokenagency/logs/` |

> **为什么 macOS 用 `~/Library/Logs` 而不是 `Application Support`**：
> 这是 macOS 上"日志"的惯例位置，用户和"Console.app"都认它。
> **为什么 Windows 用 `LOCALAPPDATA` 而不是 `APPDATA`**：日志不该跟着漫游配置文件到处跑。

文件名：`tokenagency.log`（当前写）+ 轮转后 `tokenagency.<yyyymmdd-HHmmss>.log`。

## 4.2 轮转与保留

| 项 | 默认 | 说明 |
|---|---|---|
| 单文件上限 | **8 MiB** | 超过即轮转 |
| 跨天轮转 | 是（本地时区） | 便于"按天找问题"，也避免长跑一个文件无限增长 |
| 保留份数 | **7** | |
| 保留总量上限 | **64 MiB** | 份数与总量谁先触及按谁清 |

**轮转必须在写入路径上做，且不能阻塞请求**（见 §9.1）。

## 4.3 非目标提醒

**轮转策略是纯逻辑**（给定「当前文件大小、已有份数、时刻」→「该做什么」），
所以它应当放在 `ta-core/src/diag/rotation.rs` 里**有单测**，而不是埋在文件 IO 中间件里。
**边界条件必须测**：恰好等于上限、跨天与超限同时发生、保留份数为 0/1、
磁盘上已有未知文件名（不是我们生成的，**不许删**）。

# 5. ★ 字段命名约定（本文件最重要的一节）

**全项目统一用下表这套键名。不许自创同义词。** 这是"能不能筛出一次请求的全部轨迹"的前提。

## 5.1 关联 ID

| 字段 | 类型 | 含义 |
|---|---|---|
| `request_id` | str | **一次客户端请求的全局 ID**（`req_` 前缀，已有）。**这是最重要的一个** —— 有此字段的行都属于同一次请求 |
| `job` | str | **后台任务名**（见 §5.3）。后台任务没有 `request_id`，用 `job` 标识 |

## 5.2 业务实体（**统一用 `_id` 后缀 + 一个 `_name` 供人读**）

| 字段 | 含义 |
|---|---|
| `provider_id` | 上游服务商 |
| `credential_id` | 套餐/凭据（"字节的订阅"这种） |
| `channel_id` / `channel_name` | 通道 |
| `model` / `upstream_model` | 逻辑模型 / 实际发给上游的模型 |
| `lane_id` / `node` | 线路 / 内核节点名 |
| `sub_id` | 机场订阅 |

> **为什么每个 ID 还要配一个 `_name`**：日志是给人看的。
> 只有 `credential_id: 01J8...` 的日志，排查时还要回去查库；带上名字就能直接读懂。
> **但两个都要有** —— 名字会变、ID 不会。

## 5.3 `job` 的取值（后台任务必须自报家门）

| 取值 | 谁 |
|---|---|
| `kernel_supervisor` | 内核看护（拉起/重启/退避） |
| `subscription_sync` | 订阅同步 |
| `quota_flush` | 额度账本落库 |
| `log_rotation` | 日志轮转/清理 |
| `usage_cleanup` | 请求日志过期清理 |
| `tray` | 托盘 |

## 5.4 结果与度量

| 字段 | 含义 |
|---|---|
| `code` | **`TA-xxxx` 错误码**（见 §6，硬要求） |
| `retryable` | bool |
| `status` | HTTP 状态码或内核状态 |
| `attempt` | 第几次尝试，**从 1 开始** |
| `elapsed_ms` / `ttfb_ms` | 耗时 |
| `bytes` | 字节数 |
| `truncated` | bool，字段被截断 |

## 5.5 机械检查（不靠自觉）

加一条守卫测试 `crates/ta-core/tests/log_field_guard.rs`：
扫 `crates/**/*.rs` 与 `src-tauri/src/**/*.rs`，发现**不在白名单里的** `tracing` 字段名即失败。

白名单就是本文的 §5.1–§5.4。**新增字段必须先改本文件** —— 这让约定有单一的落点。

> **为什么值得做这条守卫**：字段名漂移是**静默**发生的（没人会因为它报错），
> 而它一旦漂移，"按 request_id 筛出全部轨迹"这个能力就**部分失效**，
> 且失效时不会有任何提示。**这属于"必须机械检查"的那类约定。**

# 6. ★ 错误必须带 `code`（硬要求）

## 6.1 问题

`TaError` 的 `Display` 是给**用户**看的中文文案，**不含错误码**。
所以 `tracing::warn!(error = %e, …)` 打出来的日志**无法按码检索**。

## 6.2 裁决：**不改 `Display`**，改为**强制成对记录**

**为什么不把码塞进 `Display`**：`Display` 的文案会流向 IPC 错误信封（[10 §1.5]）与 UI toast。
给用户看的中文里出现 `TA-1001` 是**把内部编号泄漏给了用户**，且会让文案变得难读。

**规则（强制）**：

> **凡是在日志里报告一个 `TaError`，必须同时记 `code` 与该错误的其余结构化字段。**

推荐写法（**用 `%e` 记人话，用独立字段记机器可读的部分**）：

```rust
tracing::warn!(
    request_id = %rid,
    channel_id = %ch.id,
    attempt,
    code = e.code(),          // ← TA-xxxx，可 grep
    retryable = e.retryable(),
    status = e.http_status(),
    error = %e,               // ← 人话
    "通道失败，准备换下一个候选"
);
```

## 6.3 机械检查

守卫测试 `crates/ta-core/tests/error_log_guard.rs`：
扫描源码，凡是 `tracing` 宏里出现 `error = %` 或 `error = ?`，
**同一宏调用内必须有 `code =`**，否则失败并打印文件:行号。

**允许的豁免**（必须显式写在白名单里并注明理由）：
- 错误来源**不是** `TaError`（如 `std::io::Error`、`serde_json::Error`）—— 这些没有码，但要带自己的上下文。

> **这条守卫的价值**：它把"我们决定要能按码检索"从一个**愿望**变成一条**会让 CI 红的规则**。
> 没有它，这个约定会在第三次赶工时被忘掉。

# 7. 脱敏（硬要求，且要有自动化证据）

## 7.1 两道防线，缺一不可

1. **源头不产生**：`SecretString` 的 `Debug`/`Display` 已默认脱敏（`ta-secrets` 已做，很好）。
   **约定：密钥只以 `SecretString` 形式在项目中流动，绝不先解成 `String` 再记日志。**
2. **出口再扫一遍**：一个**格式化层**，对最终输出的整行做规则替换。
   它防的是"有人把密钥拼进了 message 字符串"这类绕过 —— **这是唯一能兜住未知写法的一层。**

## 7.2 规则（`crates/ta-core/src/diag/sanitize.rs`）

| 形态 | 替换为 |
|---|---|
| `sk-` 开头的长 token、`Bearer <token>` | `***` |
| `x-api-key` / `api-key` / `authorization` / `cookie` 的值 | `***` |
| `data:image/...;base64,<长串>` | `data:image/...;base64,<len=N sha256=xxxxxxxx>` |
| JWT（`eyJ...eyJ...` 三段） | `***` |
| URL 里的 `?key=` / `&token=` / `&api_key=` / `&password=` 值 | `***` |
| 我们的便携密钥库里的密文特征 | `***` |

> **图片那条要特别注意**：一张 1MB 截图 base64 后约 1.4MB。
> 它既**是**敏感内容（用户的屏幕），又会让日志文件瞬间爆炸。**必须只留长度与哈希前 8 位**（与 [07 §2.2] 同口径）。

## 7.3 证据（三条测试，缺一不可）

1. **正例**：把上面每种形态的**假密钥**（`ta-allow-fake-secret` 标记，避免撞上 pre-commit 的密钥扫描）喂进脱敏层，断言输出里**搜不到原文**。
2. **反例（同样重要）**：正常文本不许被误伤 —— 一段普通中文/代码/不含密钥的 URL **必须原样通过**。
   **过度脱敏会让日志失去排查价值，那也是一种失败。**
3. **端到端**：起一个订阅者，让它经过脱敏层，`debug!` 一个含 `?key=sk-...` 的 URL，**断言写进文件的字节里搜不到它**。

# 8. 崩溃与 panic

## 8.1 panic 钩子（必须）

`std::panic::set_hook` → 记录 `ERROR` 级日志，含：
- panic message 与 `location`（文件:行号）
- **`std::thread::current().name()`** —— 是主线程还是某个后台任务
- backtrace（若可得）
- 然后调用**原钩子**，保持默认行为不变（不要把 panic 吞掉）

## 8.2 崩溃文件（必须）

**再往 `<log_dir>/crash-<yyyymmdd-HHmmss>.log` 写一份。**
理由：panic 可能发生在日志系统自身出问题的时候，此时**不能依赖日志订阅者**。
崩溃文件用最直白的 `std::fs::write`，不经过任何异步/缓冲层。**崩溃文件永不自动删除。**

## 8.3 记录什么不记录什么

**要记**：位置、线程名、消息、当时的 `request_id`（若有）。
**不要记**：内存转储、完整 backtrace 以外的上下文（体积）。

# 9. 自保：日志不能拖垮应用

## 9.1 非阻塞写入（硬要求）

**文件 IO 绝不允许发生在请求路径上。**
用 `tracing_appender::non_blocking`，写盘在专用线程。

**必须同时处理它的代价**：非阻塞写入在缓冲区满时**会丢日志**。
所以必须**统计并暴露丢弃条数**（记一条 `WARN`，并在诊断包里体现）。
**"悄悄丢日志"和"日志里没有这条错误"是两种完全不同的事实** —— 不能让它们长得一样。

## 9.2 写盘失败不许 panic

磁盘满、目录只读、被安全软件锁住 —— 都要降级为"stderr 报一次 + 继续跑"。
**日志系统坏了不该让中转站停摆。**

## 9.3 为什么应用日志不入库（重申）

若应用日志写 SQLite：
- 写库失败 → 产生一条错误日志 → 又要写库 → **递归**
- 日志量远大于请求日志（每次内核重启、每个订阅同步都是一串），会挤掉真正有价值的请求日志

**文件是应用日志的唯一真相源**，UI 通过增量读取（tail）展示。

# 10. 级别控制（这条直接服务于"后续开发会好很多"）

## 10.1 默认

```
info,ta_gateway=debug,ta_kernel=debug
```

## 10.2 覆盖优先级

1. 环境变量 **`TOKENAGENCY_LOG`**（最高）
2. 配置 `log.level`（设置页可改）
3. 默认值

> **为什么用 `TOKENAGENCY_LOG` 而不是 `RUST_LOG`**：`RUST_LOG` 会与用户机器上其它 Rust 工具冲突，
> 而且它是**隐式生效**的 —— 用户改了别处的环境变量会让我们的日志行为莫名其妙地变。**显式命名空间更安全。**

## 10.3 ★ 热更新（不重启改级别）

用 `tracing_subscriber::reload` 句柄，**设置页改级别立即生效**。

**为什么值得专门做**：排查线上问题时，"改级别 → 重启 → 复现"往往**复现不出来**
（重启改变了状态）。能对**正在运行的进程**临时开 `debug` 是排查能力的分水岭。

**边界**：热更新只改**过滤器**，不重建 appender（否则会丢缓冲区内容、也可能泄漏文件句柄）。

# 11. 诊断包（G5：用户能交出一份东西）

## 11.1 触发

设置页 → [导出诊断包…] → 保存 `.zip`。

## 11.2 内容

| 项 | 说明 |
|---|---|
| 全部日志文件 | **写入时已脱敏**（§7.2 在写入路径上） |
| 崩溃文件 | 若有 |
| 配置 | **脱敏后**（密钥替换为 `***`，但**保留通道/线路结构** —— 结构才是排查要看的） |
| 内核生成的配置 | 脱敏后 |
| 环境信息 | OS 版本、架构、WebView2 版本、应用版本、内核版本 |
| 错误摘要 | 最近 N 条 `WARN`/`ERROR` 的码与计数 |
| `manifest.json` | 生成时间、版本、每个文件的 sha256 |

## 11.3 ★ 硬要求：**打完之后再扫一遍**

打包**结束后**，对整个包做一次全文扫描，命中 §7.2 的任何形态即**中止导出并报错**（而不是悄悄发出去）。

**有自动化测试**：造一份含假密钥的配置 → 导出 → 解压 → 断言**搜不到**。

> **为什么这一步不能省**：§7.2 是"写入时脱敏"，而诊断包还会**新加入**配置等原本不经过日志路径的内容。
> 两道防线针对的是不同入口。**"用户可以放心把它发出去"是这个功能的全部价值** ——
> 若他发出去之后才泄露，那比不提供这个功能更糟。

## 11.4 界面必须同时提供

- **[打开日志目录]** —— 往往用户只需自己看一眼，不必导出
- 明示"日志里不会有你的密钥"（因为这是用户愿不愿意点的决定因素）

# 12. 界面

## 12.1 应用日志页

**放在 [07 §2] 日志页的第二个 Tab**：`请求` / `应用`。理由：用户问的都是"刚才那次为什么失败"，
两个 Tab 在同一个页面里相邻，才能来回对照。

**能力**：实时跟随（有新行自动滚）、按级别过滤、按 `request_id` 过滤、
文本搜索、点一个 `request_id` 直接跳到"请求"Tab 的对应条目。

> **这个交叉跳转是这一页的灵魂**：应用日志说"这里报了 TA-3002"，
> 请求日志说"那次请求的 lane 是哪个、耗时瀑布长什么样"。**分开看两个都对不上，连起来看才成立。**

## 12.2 设置页的日志区（[07 §7.1] 增设）

- 当前日志级别（下拉，**改完立即生效**，§10.3）
- 日志目录路径 + [打开目录]
- 当前占用（文件数 / 总大小 / 最早时间）
- [导出诊断包…]
- [立即轮转]（排查时想切开一个干净文件）

# 13. 验收标准（我会真跑这些）

| # | 验收项 | 怎么验 |
|---|---|---|
| 1 | 日志**真的落到文件** | 起 App → 日志目录有 `tokenagency.log` 且非空 |
| 2 | **错误码可检索** | 故意触发一个已知错误 → 在日志文件里 `Select-String 'TA-\d{4}'` 能搜到对应码 |
| 3 | **不泄露密钥** | 配置里放一个假 key → 触发一次相关请求 → 全文搜不到它 |
| 4 | **关联可追** | 取一个 `request_id` → 能筛出跨 ingress/pipeline/dispatch/meter 的多行 |
| 5 | **崩溃有据** | 人为 panic 一次 → `crash-*.log` 生成，含位置与线程名 |
| 6 | **诊断包安全** | 导出 → 解压 → 自动扫描无密钥（§11.3 的测试） |
| 7 | **热更新生效** | 运行中把级别改成 `debug` → 不重启即出现 `DEBUG` 行 |
| 8 | **不阻塞请求** | 高并发下写日志不显著增加请求延迟；缓冲区满时**有丢弃计数** |
| 9 | **轮转正确** | 单测覆盖 §4.3 的四个边界；**磁盘上已有的非我们生成的文件不许被删** |
| 10 | **字段名守卫** | 故意写一个不在 §5 白名单里的字段名 → 守卫测试必须红 |

## 与既有工作包的关系

- **[07 §2] 请求日志**：不动。应用日志是另一条路。
- **G4（trace + events）**：`ta-gateway` 的 `trace.header_diff` 等继续走 SQLite；
  应用日志负责"过程轨迹"。**两者通过 `request_id` 关联**（§5.1）。

  **必须早于任何可能失败的初始化**，否则"初始化失败"这件事本身没有日志。
