# 35 · 「自动」出口的**人工验证清单**（在你自己的机器上跑，约 5 分钟）

**为什么需要你跑**：本仓库的自动化环境里**没有内核可执行文件**
（scratch 配置 `kernel.path = null`，PATH 里也没有 mihomo），
所以"按服务商 `base_url` 测延迟、选最低那条、并且粘住不换"这条链路**在我这边无法真机验证**。
这一页是给你照抄的步骤 —— 全程**不改代码**，只点界面 + 看两个地方。

## 0. 前置（缺一不可）

| 需要什么 | 怎么确认 |
| --- | --- |
| 内核可执行文件（mihomo） | 设置页里能填内核路径；填完状态应变成"运行中"（不是"未运行"） |
| 至少**两份订阅**（或一份订阅里有多个节点） | 网络页订阅列表里能看到节点数 |
| 至少一个服务商 + 它的凭据 | 服务商详情页能"测试连接"成功 |

## 1. 步骤（每步都给"应该看到什么"）

1. **把服务商的代理设成「自动」**
   服务商详情页 → 「网络代理」下拉 → 选 **自动**（有多份订阅时会写成「自动（订阅名）」）→ **保存**。
   *应该看到*：保存成功；下拉里那一条显示为「自动」。

2. **确认库里真的长出了那条线路**
   网络页 → 线路列表里应出现一条名叫 **自动** 的线路；
   它的类型是"整份订阅择优"、**组类型是 `select`**（不是 `url-test`）。
   *为什么盯这个*：`url-test` 会自己周期性换出口 —— 那正是要避免的（封号风险）。

3. **触发一次重算（两种都要试）**
   * **手动**：网络页 → 订阅那一行点 **刷新**；
   * **自动**：什么都不做，等最多 6 小时（或把该订阅的"更新周期"临时改小，例如 60 秒）。

4. **看日志**（设置页 → 打开配置目录 → 同级 `logs/tokenagency.log.*`）
   *成功时*：`「自动」出口已重算` + `status=first_time`（首次）或 `status=same_address_still_there`（粘性命中）；
   *内核没跑时*：`「自动」出口重算失败（这一家跳过）` + `error=…内核没在跑…`（这条是**如实拒绝**，不是 bug）。

5. **看内核里到底选了谁**（关键一步）
   内核的 `/proxies` 里找到那条自动线路对应的组，看它当前选中的节点名。
   *应该看到*：选中的是**延迟最低**的那个节点（可与你在内核界面里看到的节点延迟表对照）。

6. **验粘性（用户最在意的那条）**
   * 记录**第 5 步选中的那个节点的地址（IP/主机名）**；
   * 让订阅**再更新一次**（手动点刷新即可，或等自动）；
   * 再看一次内核 `/proxies` 的选中项。
   *应该看到*：只要那个地址**还在新订阅里**，选中的**仍然是它** —— 哪怕出现了延迟更低的节点。
   这正是"出口 IP 不会无故变化"。

7. **反向验证（可选，但很有说服力）**
   把那个节点从订阅里删掉（或让它连不通），再刷新一次：
   *应该看到*：这次**换了**节点，且日志里的理由是 `previous_gone` 或 `previous_unreachable`
   —— 也就是**只有这两种情况**才会重挑。

## 2. 结果怎么反馈给我

把这三样贴给我即可（都不含密钥）：

1. 第 4 步的日志行（`「自动」出口已重算 …` / `…重算失败…`）；
2. 第 5/6 步内核 `/proxies` 里选中项的前后对比；
3. 如果哪一步和"应该看到"不一样 —— 那一步的截图。

我据此要么确认 E 期收口，要么直接定位（日志里有 `provider_id` / `status` / `attempt`，
足够把问题收窄到"探测" / "裁决" / "写内核" 三者之一）。

## 3. 我这边同时会做的（不依赖你的机器）

**B 方案**：给内核控制器抽一个**可注入的探针**，让"探测 → 裁决 → `set_select` → 记住地址"
整条编排能在 CI 里被回放验证（给一组人造延迟表，断言选中的是哪一个、以及第二次调用是否粘住）。
代价 1–2 轮；好处是这条链路从此在 CI 里有证据，不必每次靠人工。

## 8. 2026-09-26 真机复核结论（**准确到什么程度、缺在哪里**）

> ⚠️ 本节在 [docs/46 §297] 之后**整段重写过**：上一版写的"本机没有公网 ⇒ 最小延迟在这台机器上
> 无法证明"是**错的**（[docs/46 §287] 已更正：本机有公网，`generate_204 → 204`）。真正卡住 E 期的
> 不是环境，而是**应用探测走错了 REST 路由**（provider 的节点不在 `/proxies` 顶层，
> `/proxies/<name>/delay` 对它们全 404）—— 修完以后同一条机器上就拿到了结论。

### 已经**真机证明**的（`target\verify\tokenagency.exe`，`PASS=30 SKIP=1 FAIL=0`）

1. **「自动」出口真的按"实测最低延迟"选，而且真的写进了内核**（`step29`，**用户给的真实订阅**）：

```
应用判决：「自动」出口已重算 provider_id="ta-e2e-2" status="manual_refresh"
          node="剩余流量：7.97 GB" probed=34 measured=30 probe="https://www.gstatic.com/generate_204"
内核组 now = 剩余流量：7.97 GB                    ← 与应用日志**逐字一致** ⇒ set_select 真的生效
挂具用同一张表（provider 的 history[].delay）核对：32/34 条有值，其中该节点 169ms
                                              ⇒ 它是这张表里**最低**的那条
```

   三个要点都可单独核对：`measured=30`（不是"没量到"）、`probe=` 就是**服务商 `base_url`**
   （不是别的地址）、`now` == 应用日志里选的那条（写的那一半也成立）。
2. **触发点②（用户手动刷新）真的会触发重算**：上面那条 `已重算` 就是点
   `network-subscriptions-refresh` 之后产生的 ✓（`status="manual_refresh"` 是裁决理由）；
3. **组必须是 `select`**：挂具从库里读到 `lane-ta-e2e-sub-form-auto` 的
   `group_type="select"` ✓ —— 这是 `set_select` 能生效的前提（`url-test` 组会返回 204 但 `now` 不变，
   [docs/46 §297] 实验 ⑦⑧）；
4. **全不通时如实报告**（历史证据，仍然有效）：`status="all_unreachable" node="(未选)"`，
   `measured=0` —— 一个字节都不写 [docs/29 §2.2] ✓；
5. **探测失败与"选错"分得开**：日志行里的 `measured` / `probe` 两个字段就是分界线
   （`measured=0` = 探测没跑起来；`probe=` 不一致 = 用错了探测目标）。

### **没有**证明的（如实标注，不写成通过）

1. ~~「自动」的粘性（订阅更新后不换 IP）~~ → **已在真机上拿到证据**（`step30` PASS，2026-09-27）：
   把订阅周期压到 1 秒后**冷启动**应用，让**应用自己的后台同步任务**（`manual = false`，触发点①）
   去刷一次；观察到的两轮判决是
   `previous_unreachable`（上次那条这次确实没量到 ⇒ 按规则重挑）→
   `same_address_still_there`（新基准上**沿用**），且内核组的 `now` 与日志里的 `node` **逐字相同**
   ⇒ **出口 IP 没变** ✓。见 [docs/46 §301]。
   仍未做到的：让"上一次那条一直量得到"连续 10 分钟不换（本次只观察到一轮沿用就收工）。
2. **夹具档（`step28`）的"400ms 差距"判据**：本轮 `SKIP` —— 内核经挂具那两条**本地转发代理**
   探测时，14 条节点**一条延迟都量不出来**（探测目标换成公网 gstatic 也一样，14 条全 0）；
   而同一台机器上、同一时刻，**真实订阅**的 34 条节点能量到 26–30 条 ✓。所以这是**挂具夹具的局限**
   （具体原因还没定位：内核经这两条 `type: http` 本地代理走"绝对 URI 明文转发"/CONNECT 时的行为
   与真实节点不同），**不是产品问题**，但**也还没有定论** —— 已如实记成 SKIP 而不是 PASS。
3. **多家服务商共用同一条「自动」线路**（用户可配出来）：每家会按自己存的地址独立重算、写同一个组，
   `now` 变成"最后写的那家"的选择。**要不要在界面上拦/提示，属于产品决定**（记在 [docs/31]）。

### 需要**产品方拍板**的一件事（我没有擅自改）

`step29` 里应用选中的是订阅里那条**信息节点**（名字形如 `剩余流量：7.97 GB`）。它确实是这张表里
最低延迟的一条（169ms），按 [docs/29 §2.2] 的字面规则"在整份订阅里挑最低延迟"**完全正确**；
但很多机场把这 3 条（剩余流量 / 套餐到期 / 过滤掉 N 条线路）当作"展示用"的伪节点。

要不要把它们排除在「自动」的候选之外，是**产品的语义选择**（排除掉可能把一条真能用的快节点
也排除，不排除则用户可能拿到一条名字很怪但真能用的出口）——见 [docs/31] 的待拍板清单。
若决定排除，实现只有一处：`src-tauri/src/commands/net.rs` 里构造候选前按名字过滤。
