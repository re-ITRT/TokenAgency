## 1. 本轮定死的口径

### 1.1 三个实体，三种归属

| 实体 | 谁定义 | 归属 | 说明 |
| --- | --- | --- | --- |
| **服务商** | 用户 | 配置 | 一个服务商 → 多条**线路** |
| **线路**（通道） | 用户在**服务商界面**管理 | 归属服务商 | 一条线路 = `(服务商, 凭据, 上游模型名, 线路/代理, 权重, 优先级, 能力元数据)`；**一条线路可以给多个模型提供** |
| **模型** | 用户在**模型页**创建 | 归属"本地对外暴露" | 一个模型**记录自己该向哪几条线路要数据**（多对多，**由模型这一侧持有**）；一个模型可以由多条线路构成 |

**关键翻转**：关系的**持有方在模型侧**（"一个本地暴露的模型，记录了自己该向那一条线路要数据"）。
这直接决定删除语义：删模型不动线路（线路归服务商），删线路要把它从各个模型里摘掉。

### 1.2 删除只往一个方向传

* **删线路**（在服务商界面）：线路消失 → 从**所有**模型的线路表里摘掉它。
  * 摘完还有别的线路 → 模型继续活着，路由变窄（并在结果区如实说明"某模型少了一条线路"）。
  * 摘完**一条都不剩** → **模型自动删除**（用户原话："如果删了之后模型没有可用线路，直接也把模型也删了"）。
* **删服务商**：等于把它名下的线路全删掉（同上，逐个模型摘；没线路的模型跟着消失）。
* **删模型**：**一条线路都不动**（用户原话："不要动线路，那些，模型只会被线路影响"）。

### 1.3 能力兼容是**单向**的（用户给的反例）

* 模型声明了某项能力（例如 vision / 上下文长度）→ **它用的每一条线路都必须满足**，否则拒绝（`TA-2007`，逐字段列出差异）。
* 线路**比模型更强**是允许的（"往没有 vision 的模型里面加一个带 vision 的线路是可以的，用不上至少不会错"）。
* 所以判据从"同 model 的线路必须**相等**"改成"**模型 ⊆ 每条线路**"。

### 1.4 模型信息从哪来（以及今天的硬限制）

用户的原话是"要的信息从服务商扫描那里就已经本地有了"。**今天这不成立**（§0）：
上游 `/models` 对绝大多数服务商**只返回 id**，我们也没读别的字段；`ollama` 的详细能力要走它自己的
`/api/show`，火山的 Ark 接口通常也不给上下文长度。

因此本轮的做法（HONEST）：

1. **扫描把上游返回的那一条模型对象原样记下来**（不只取 id）：能读到的字段就逐字存（`owned_by` / `created` /
   `context_length` / `capabilities`… 上游给什么记什么），读不到的就是**没有**；
2. 模型的对外信息 = 我们模型页上定义的那份，字段**来自**它的线路所记录的、上游真实给出的那部分；
3. **上游没给的字段，我们一个都不编**（不填默认上下文长度、不猜 vision）。这一条必须在界面上说出来：
   模型详情里给"上游没提供这些字段"的空态，而不是一排 0/false 冒充"已知"。
4. 设置页那个「对外暴露模型能力标签」开关**删掉**（它没有任何运行时读取者；能力信息本来就该随
   `/v1/models` 一起给）。

### 1.5 向导默认扫描

进向导第 2 步**自动扫一次**（不需要点按钮），过程中显示"正在扫描上游…"；按钮保留为"重新扫描"。

## 2. 分期（每期都要能独立跑绿，不留半成品）

| 期 | 内容 | 状态 |
| --- | --- | --- |
| **R1（本轮）** | ①删模型不再级联删线路（线路被拒绝保护）；②删服务商 → 摘线路 → **没线路的模型自动删掉**；③向导进第 2 步自动扫描 + "正在扫描" | 见 §3 |
| **R2** | 关系翻转：`Model` 持有 `lines: [channel_id]`（多对多），`ChannelConfig.model` 退场；校验器/路由/内核生成/策略/界面全部跟着改 | 未做 |
| **R3** | 模型页：创建模型必须选 ≥1 条线路、权重/粘性配在模型页（值存线路上）、模型详情页；能力兼容改单向 | 未做 |
| **R4** | 扫描记录上游模型对象原文；`/v1/models` 返回**我们的模型**（字段来自所记录的元数据）；删掉那个死开关 | 未做 |

> 为什么 R1 与 R2 分开：R2 会把 `channel.model` 从配置里拿掉，牵动校验器、路由引擎、
> 内核配置生成、策略、以及现有配置的迁移 —— 那必须是**一期完整的改动**，
> 不能和"先把过宽的级联收窄"混在一起（混在一起就没人能说清哪一步坏的）。

## 3. R1 落地要求

1. `model_delete{force}`：**永不删线路**。被线路引用时 **`TA-5002`**（无论 force），
   人话说明"线路是从服务商那边定义的，模型只负责用：请先在服务商界面删掉指向它的线路（或删服务商），
   最后一条线路消失时这个模型会自动消失"。`force` 只用来级联删**通道组**那些容器引用。
2. `provider_delete`：现有级联（凭据/通道/组引用/策略 `provider_in`/定价/目录行）不变，
   之后**多一步**：把"一条通道都不剩"的模型删掉，并在 `tracing` 里如实记下删了哪几个。
3. 前端：删除确认框的"会连带影响"里把这条语义**先说出来**（承诺必须是真的）。
4. 向导第 2 步：进入即自动扫描一次；pending 文案沿用 `providers.wizard.scanning`。
5. 测试：
   * Rust：删模型被线路引用 → `TA-5002` 且**配置一字未改**；删服务商 → 线路没了、**没线路的模型跟着没了**、
     还有线路的模型**完整保留**；`channel_delete` 之后若该模型再无线路 → 模型自动消失。
   * 前端：确认框里那句话在；向导进第 2 步自动发出 `model_import_from_provider` 且显示"正在扫描"。

* **关系仍然是"线路 → 模型"**（`ChannelConfig.model` 还在）：所以"删模型不动线路"目前表现为
