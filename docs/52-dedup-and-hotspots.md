# docs/52：有证据的重复收敛与热点修复

用户第 319 轮：**「这一轮请从 可拓展性 简洁性 易读性 性能 几个方面按需重构代码」**。

「按需」是这一轮的方法论约束：**先机械测量，再决定改哪儿**。所以本文件的结构是
"测到了什么 → 所以改了什么 → 没改什么、为什么"。

上一轮（[docs/50](50-plugin-and-capability-minimization.md)）也做过一轮结构清晰化，
但**那一轮没有给收敛下来的共享件配守卫** —— 于是同一个毛病又长回来了
（本轮实测：光"读后端原始对象"这一件就长出了 **21 份定义**）。这一轮补上了守卫。

---

## 1. 测到了什么（机械测量，不是感觉）

四个维度各用一条脚本/命令量，量完再决定动不动。

| 维度 | 怎么量 | 结果 |
|---|---|---|
| 简洁性 | 全仓扫同名函数定义 | **21 份读件定义**、`StatItem` 4 份、`i18nKey` 3 份、`mergeHelpText` 2 份、阈值 `12` 2 份 |
| 性能 | 扫渲染回调内的线性查找 | `apikeys` 用 `selected.includes()` 做逐行勾选判定（**O(行数 × 勾选数)**，每次渲染重算）；`models` / `providers` 已用 `Set` |
| 易读性 | 按"大括号配平"量函数长度 | ≥100 行的函数 **57 个**，最大的几个是页面级 JSX 组件（726 / 691 / 626 / 571 / 531 行） |
| 可拓展性 | 看"加一个新页面/新字段要改几处" | 读件各页自己写 → 新页面必然再抄一遍；且**已经漂了** |

### 1.1 测量本身踩的坑（如实记录）

第一版长度扫描器报出「`apply_onboarding` 有 902 行」和「`due_subscription_ids` 有 2002 行」。
手工核对后**两个都是假的**：真正的行数是 **125** 和 **26**。

原因：扫描器把 Rust 的**生命周期** `<'a>` 当成了 char 字面量的开头，
于是把从 `'a` 到**下一个 `'`** 之间的整段代码当字符串吞掉，括号配平随之全乱。
`${secret:…}` 这类字符串模板与 `match` 分支也会加剧它。

> **教训**：机械测量的**工具本身也要被校验**。这次是靠"挑两个最大的手工数一遍"发现的 ——
> 如果直接照着 902 行去重构，就会把力气花在一个 125 行的函数上（甚至把它拆坏）。
> 修正后（正确识别生命周期与 char 字面量）再量，得 57 个 ≥100 行的函数。

## 2. 改了什么（只改有可验证收益的）

### 2.1 简洁性 + 可拓展性：读件收敛（21 份 → 1 份）

`asRow` / `pickStr` / `pickNum` / `pickBool` / `pickArr` / `hasKey` 在
**5 个页面 model 里各写了一遍**：

| 读件 | 份数 |
|---|---|
| `asRow` | 5 |
| `pickStr` | 5 |
| `pickNum` | 5 |
| `pickBool` | 4 |
| `pickArr` / `hasKey` | 各 1（都只在 `network`） |

**而且已经漂了** —— 两份 `asRow` 语义不同：

| 文件 | `asRow([])` |
|---|---|
| `network/model.ts`、`settings/model.ts` | 返回那个**数组**（`typeof [] === "object"`） |
| `providers/model.ts`、`providers/editor.ts`、`providers/detail.tsx` | 返回 `{}` |

这是这次重构**唯一需要做判断**的地方：收敛必须选一边，选错会让某个页面的行为静默变掉。

**选「数组不是一行」**，理由是可验证的而不是偏好：
收下数组并不比挡掉它多读到任何东西（`arr["model"]` 恒为 `undefined`），
所以对既有调用点**行为等价**；唯一区别是把"拿一整个列表当一行用"这种错暴露得更早。
这条理由写成了可执行的断言（`src/app/row.test.ts`），不是注释。

新实现 `src/shared/row.ts`（105 行）带齐 7 个读件，其中 `pickRows` 是**新加的**：
`pickArr(...).map(asRow)` 这个形状在 5 个 model 里反复出现，而手写版本有两种错法
（忘 `?? []` 直接抛、忘逐项收窄）。

### 2.2 简洁性：另外四组重复

| 形状 | 前 | 后 | 唯一实现 |
|---|---|---|---|
| `StatItem` | 4 份（3 份逐字相同 + `models` 多一个 `testId`） | 1 份（取并集，`testId` 可选） | `shared/components/StatItem.tsx` |
| `mergeHelpText` | 2 份（逐字相同） | 1 份 | `shared/helpTip.ts` |
| `sectionHelpMode` / `collectIntoHelpTip` / `HELP_TIP_MIN_LENGTH` | 各 2 份，且阈值在一处是**裸字面量 `12`** | 各 1 份 | `shared/helpTip.ts` |
| `i18nKey` | 3 份（逐字相同） | 1 份 | `shared/i18n/index.ts` |

那两处阈值值得单说：同一个数字写在两个文件里，**改一处就会让两个页面的问号
出现/消失的时机不一致**，而这种不一致**没有任何测试会红**（各页只测自己那一页）。

> `i18nKey` 我一开始判为"纯多余的恒等转换"，打算全删。机械核对 62 处字面量调用后发现
> **判断错了**：它真正的作用是**阻止字面量类型被拓宽**（`const K = { a: "x.y" }` 里
> `K.a` 是 `string`，不经过它过不了 `t()` 的类型约束）。所以它是必要的收口，
> 只该有**一份**而不是三份 —— 已按"收敛"而不是"删除"处理。

`network/index.tsx` 与 `settings/index.tsx` 保留了 `mergeHelpText` / `sectionHelpMode` 的
**再导出**：兄弟模块与 `settings.test.tsx` 都是从那两处取的，直接删会让它们编译失败
（与上一轮 `DASH` 那次同一个教训：**删导出必须让编译器过一遍**）。

### 2.3 性能：`apikeys` 渲染期的 O(N×M)

这一页在表头全选判定和**每一行**的复选框上直接扫数组：

```tsx
rows.every((row) => selected.includes(row.id))   // 表头
checked={selected.includes(row.id)}              // 每一行
```

都是 **O(行数 × 勾选数)**，而且每次渲染重算。
同仓的 `models` / `providers` 两页**早就**用了正确写法
（`const selectedSet = useMemo(() => new Set(selected), [selected])`），只有这一页漏了。
已对齐：`selectedSet` + `.has()`，`targets` 也随之改成 `Set` 查。

> 这一条是**本轮唯一的产品代码性能改动**。它是"同一仓里已有正确写法、只有一处漏了"
> 的类型，收益随行数增长 —— 不是"顺手优化"。

### 2.4 可拓展性：把教训变成守卫（这一轮的重点）

新增 `src/app/rowReaders.guard.test.ts`（139 行），扫描**全仓**（测试文件除外）：

1. 除 `shared/row.ts` 外，任何源码不许再定义那 7 个读件；
2. `shared/row.ts` 必须**确实**提供全部 7 个（防止有人删掉一个而守卫仍绿）；
3. 本轮收敛的其它单件（`StatItem` / `mergeHelpText` / `sectionHelpMode` /
   `collectIntoHelpTip` / `i18nKey` / `HELP_TIP_MIN_LENGTH`）也不许被重新定义 ——
   **再导出是允许的**（兄弟模块要靠它编译）；
4. 单件清单里每个 `home` 文件都**真的**定义着那个名字（防止清单指向不存在的实现）。

**为什么这一条值得单独做**：上一轮收了 `Caption` / `DASH` / `SECTION_SX` / `SwitchControl`，
但没配守卫，于是这一轮又扫出 21 份新的读件重复。
**收敛不是一次性的动作，是要被机器持续保护的**。按函数名扫描而不是列文件白名单，
是为了新增页面时不用维护任何清单。

## 3. 没改什么，以及为什么（「按需」的另一半）

「按需重构」的诚实含义是：**测出来是热点，但不等于就该动**。以下都**刻意没动**：

| 项 | 实测 | 为什么不动 |
|---|---|---|
| 6 个 ≥500 行的页面级 JSX 组件（`ProviderDetailBody` 726 行、`LogsBody` 691 行…） | 最大的易读性热点 | 拆 JSX 组件是**纯搬运**：没有测试能证明拆完更对，而回归风险是实打实的（这一轮的写作用域也要留给别的事）。**要拆应当单独一轮，配该页的交互测试**。 |
| `apply_onboarding`（真正 125 行） | 曾被误报 902 行 | 它是**线性流水线**（写仓库 → 落配置 → 读回一致），顺序本身就是语义。拆成小函数会让"密钥只在局部变量里出现"这条安全属性更难核对。 |
| `PricingEngineImpl::new` 在 `resolve_price` / `build_channel_matrix` 里每次重建 | 看着像性能问题 | **每请求路径不受影响**：网关在装配时建一次（`gateway.rs`），`meter.rs` 走的是那份。上面两处是**低频 IPC 命令**（用户点一下），不在热路径。改了收益测不出来。 |
| 内置价表 `builtin_lookup` 的线性扫描 | 表长只有几十条 | 无实测收益。**没有测量支撑的优化就是猜**。 |
| 其它 `pickStr` 式的多键并集读法 | 看着啰嗦 | 那是**契约与实现键名不一致**时的有意并集（`logs/model.ts` 顶部整张表记录了偏差），不是重复。 |

## 5. 结论

* **简洁性**：21 份读件 → 1 份；`StatItem` 4→1；`i18nKey` 3→1；
  `mergeHelpText` / 阈值 / `collectIntoHelpTip` 各 2→1。
* **可拓展性**：新页面不再需要抄读件；并且**有守卫拦着**不让它再长回来。
* **易读性**：删掉重复的同时，把"为什么是这一边"（`asRow` 的口径）写成了断言而不是注释。
* **性能**：修掉 `apikeys` 渲染期的 O(N×M)（唯一有测量支撑的一处）。

**没有做的**：那些 ≥500 行的页面级 JSX 组件**仍然是那么大**。它们确实是易读性热点，
但拆分是纯搬运、需要单独立项配交互测试 —— 这一轮刻意没碰，不假装已经解决。
