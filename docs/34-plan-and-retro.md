### 哪一块最耗时、为什么

1. **最耗时的是"删/改一处界面元素"这类小任务** —— 反直觉，但它要求**同时**做对三件事：
   找到**唯一的**锚点、改**完整**的块、**证明它真的生效**。我前两项经常靠"猜文本"，第三项经常靠
   "`tsc` 过了就算"——而 `tsc` 对"列头多一项"、"载荷少一个键"、"探针没断言"**一律不报**。
2. **第二耗时的是真机验证环节**：E2E 本身 2.5–3 分钟不算贵，贵的是**探针写错要重跑**
   （改一次 + 跑一次 = 0.5 轮）；本会话有 3 次是"探针自己坏了"而不是"功能坏了"。
3. **第三是环境类误判**：旧前端包、WAL 还原、SQLite 表名列名 —— 每次都要一次额外的排查往返。

### 根因（一句话）

> 我把"**改**"当成了主要工作，把"**证明改对了**"当成收尾动作。
> 但这个仓库里"改"是静默的（替换失败不报错、`tsc` 不报语义缺失），
> 所以**证明必须是设计的一部分，而不是事后补的**。

## 二、新的固定节奏（每轮 7 步，从下一轮起执行）

1. **选一片**：只从计划表里取一片（不许顺手多做）；
2. **先写断言**：动手前先写清"怎么证明它成了"（哪个 testid、哪条日志、哪条 SQL 断言）；
3. **read 目标块**：把那一段**原样读出来**（不做任何推测）；
4. **整块替换**：用 read 到的原文做替换（**禁止行号拼接**；替换后立刻 `node --check` / `tsc`）；
5. **跑该屏/该 crate 的测试**（快，几秒到十几秒）；
6. **只在需要真机证据时跑 E2E**（否则省 3 分钟；跑之前先把探针写成"会失败"的样子验一遍）；
7. **更新 docs/31 + 报告**（进度 / 本轮 / 剩余 / 预计轮数 / 预计工时）。

**三条硬规矩**（对应上面的返工账）：

* 改代码只走「read → 整块替换」；**替换后必须有断言**证明结果（不许只看 `tsc`）；
* 探针必须**判**点击结果与后端回执，且插进目标函数体内（先 read 确认作用域）；
* 任何"前端改动"的验证一律用 `scripts/build.ps1` 的产物（release），**不用** debug 包。
